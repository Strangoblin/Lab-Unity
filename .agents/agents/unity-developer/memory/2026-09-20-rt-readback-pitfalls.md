# 2026-09-20 — RT 回读与画面判读的四个陷阱（一次误判的完整复盘）

## 事件

做 PCSS 性能档的换档冒烟测试时，回读 `_PCSS_ShadowCacheTex` 得到「四个 tile 全零」，
据此断定 **caster 光栅 pass 无输出、PCSS 对画面零贡献**，并打算按「存量缺陷」上报。
**结论是错的。** 用户一句「开 debug 是有阴影图的」触发复核，最终查明 atlas 内容正常。

误判的代价：一条基于错误结论的 memory + 一次差点让用户去查一个不存在的 bug。

## 四层错误，逐层都比上一层隐蔽

### 陷阱 1（表层）— 采样面积太小

第一遍读的是**每个 tile 正中心 64×64 的方块**。tile 是 1024×1024 → 64×64 只覆盖 **0.39%**。
几何体在正交投影里落哪块区域完全没保证，正中心恰好是空地。

> 铁律：判断「一张 RT 是不是空的」，**必须全图统计**，不能抽样。
> 全图 = `ReadPixels(new Rect(0, 0, rt.width, rt.height), ...)`。2048² RFloat 也就 16 MB，读得起。

### 陷阱 2（中层）— 控制组只证明了「读法能读」，没证明「读的是对的东西」

做了两层控制组，**都通过了**，于是产生了虚假信心：

1. 格式层：自建 RFloat RT 写已知值 0.5 → 回读 0.5 ✓
2. 内容层：同一效果里确定有输出的屏幕空间三张 RT → 4096/4096 全非零 ✓

但这两层只能排除「格式不支持」「读法/时机错误」，**排除不了「这个资源此刻本来就该是空的」**。
控制组通过 ≠ 被测结论成立。

### 陷阱 3（根本）— 「空」可能正是正确答案

真正的原因：**场景里 16 个投射物体的距离全部落在 24.7–33.0 m**。
而 High 档的 PSSM split（`pssmLambda=0.75`，near=0.3，far=50，4 级联）算出来约 **(4.0, 9.2, 19.8, 50)**：

| 级联 | 覆盖 | 物体数 |
|---|---|---|
| 0 | 0–4.0 m | 0 |
| 1 | 4.0–9.2 m | 0 |
| 2 | 9.2–19.8 m | 0 |
| 3 | 19.8–50 m | **16（全部）** |

所以 **tile0/1/2 空、tile3 有内容是完全正确的**。查询时只看到「三块空」，就当成缺陷。

> **铁律：判「资源为空 = 缺陷」之前，先问「在当前的场景 / 档位 / 相机位姿下，它本来就该是空的吗」。**
> 分块 / 分级联 / 分 mip 的资源，**空与否是场景状态的函数**，不是实现的属性。

> **同日复发（当天第二次）**：记录 unityctl 坑时，我又由一次「文件没出现」断言
> `screenshot capture`「**文件从不落盘**」，复查后发现有 1/5 次其实写成功了。
> 形态与本陷阱完全相同，只是对象从 RT 换成了工具输出。
> **通用形式：单次否定观察不足以下「从不 / 恒为」这类全称断言。**
> 要么多试几次给出比例，要么把断言降级成「本次未观察到」。
> 详见 [2026-09-20-unityctl-tool-pitfalls.md](2026-09-20-unityctl-tool-pitfalls.md) 坑 1。
> 可执行判据：把「期望有内容的那部分的输入条件」量化出来再对照——
> 本次就是 `物体到相机距离` vs `各级联 far plane` 这张对照表，一算就清楚了。

附带教训：**相机位姿在会话之间会变**。第一次测「cascade 0 视锥内有 7/16 物体」时相机在
`(7.64, 2.15, 9.83)`，复核时在 `(19.09, 5.97, -7.80)`。拿跨时刻的两次测量互相印证是无效的。

### 陷阱 4（感知层）— 把「目视判读的印象」当成了证据

前三个陷阱都在代码里，第四个在眼睛上。Debug 直出的截图是**接近平光的浅灰、暗部极弱**
（实测阴影值只在 0.76–1.00）。我看了这张图，把它读成「没有阴影」——
于是它与「四个 tile 全零」互相印证，闭环成一个自认为"确定"的结论。

但那张图跟「阴影正确、只是很淡」是**完全相容**的。弱信号画面本身就是**歧义**的，
它支持不了任何一个方向的结论；而人在已有假设下，会把它读成支持自己那一侧。

> **铁律：图像不构成证据，除非先量化「期望信号应该有多大」再比对。**
> 顺序必须是 **算期望 → 定阈值 → 再看图**。反过来（先看图形成印象、再找理由）
> 只会不断加固错误结论。

形式化判据：本次的期望信号由
`物体到相机距离(24.7–33.0m) → 落哪一级联 → 半影尺度 → 阴影值量级`
这条链算得出来；算完就知道「淡」是正确结果，**「没有」才是异常**。

## 复用手法 — RT 内容回读的正确流程

```csharp
var tex = new Texture2D(rt.width, rt.height, TextureFormat.RFloat, false);  // 格式须匹配
var prev = RenderTexture.active;
RenderTexture.active = rt;
tex.ReadPixels(new Rect(0, 0, rt.width, rt.height), 0, 0);   // 全图，不抽样
tex.Apply();
RenderTexture.active = prev;
// 按 tile / 分块统计：nonzero 数、min、max、以及关键——**分布**（内容在哪）
```

三步缺一不可：

1. **全图**统计，并按分块（tile / 象限）分别报，这样能直接看出「哪一块有、哪一块没有」
2. **控制组两层**：格式层（自建同格式 RT 写已知值）+ 内容层（同效果里确定有输出的另一张 RT）
3. **期望值对照**：把「应该有内容」的输入条件量化，和实测对照。空 = 缺陷，只在「期望非空」时成立

补充判据（本次用上的一个反向推理）：**`_PCSS_AtlasParams` 是否真的到达 shader，
可以从输出是否有 INF/NaN 反推**。若该 uniform 未绑定则为 0，`.x = 0` 会让
`20.0 * halfW0 / _PCSS_AtlasParams.x` 变成 INF、`maskUV = maskPixels * 0` 变成 0，
画面必然是 NaN/INF 垃圾。实测 min=0.7642 / max=1.0000 全部有限且干净 → **uniform 确实到达了**。
这比「相邻行绑定的 `_ScreenSize` 能用所以它也能用」的同构推理更强。

## 本轮实测到的正面事实（可用作基线）

- Low 档实跑：`ShadowRT=1024x1024`、`CascadeCount=2`、`CascadeSplits=(6.04, 30.00, 0, 0)`、
  `PCSS_LOW=True PCSS_MEDIUM=False` —— 档位驱动的四个量全部在运行期生效。
- High 档 atlas 全图 4194304 像素中 `nz=2535`，全部在 tile3，深度范围 `[0.5101..0.5161]`。
- `_PCSS_SoftShadow`（642×522）R 范围 `[0.7642..1.0000]`，32 像素非全亮、33 个 penumbra 像素；
  **三次连续回读数值完全一致** → 回读是确定性的（但确定性 ≠ 正确，见陷阱 3）。
- 屏幕截图与上述测量一致：接近平光的浅灰，暗部极弱。这是因为物体都挤在最远级联，
  且部分已接近覆盖边界 → 半影被放得很大 → 阴影很淡。**属预期，非缺陷。**

# 可持续开发判断

目标：新增相近功能时，改动范围可解释、旧行为可验证，重复开发的成本逐步下降。允许真实需求修正抽象，让重构集中在明确的职责边界。

## 何时取用

- 新功能 / 效果的第一版、已有能力扩展、结构重构：在设计或首次实施前取用；没有同类实现时同样适用。
- 已定位的局部修复、参数 / 文字 / 格式小修：只核对实际影响的行为与边界，通常一句话沿用现有设计即可；修复若改变接口、资源所有权或职责分工，再补相关判断。
- 同一任务与后续迭代复用已读内容和已有设计说明；需求、范围或结构假设变化时更新受影响项。

把结论并入现有计划或开工说明，深度随任务规模调整。无需另建一份方案文件或增加门禁、审批节点；不据此扩展任务授权。

## 首次实施前的判断

1. **选真实基线。** 从当前功能族索引取一个合适的模板或已验证实现，读取实际代码与契约，说明沿用什么、为何偏离。首次功能在相关范围内未找到基线时如实说明，先做满足当前目标的局部实现。同类源码比较沿用 [复用流程](../../unity-feature-reuse/SKILL.md)，已有比较结论直接复用。
2. **区分稳定约定与暂定选择。** 输入输出语义、资源所有权、既有引用、用户要求的默认行为等，可作为要保持的约定，并注明依据。当前只支持一种输出、当前资源尺寸等实现选择应写清适用范围；未证实的猜测保持为假设，不自动固化为公共限制。
3. **走查近期变化。** 选用户计划或真实相邻实现支持的一两个可能变化，说明它会改哪里、影响谁、如何验证；通常先做纸面走查即可。信息不足时写“未知”，保留局部实现，不编造未来需求或预建插件、开关、接口。
4. **明确职责与状态归属。** 看清共享输入 / 调度、资源生命周期、算法、设置与预览分别由谁持有。把最可能变化的部分放在可独立替换的位置；原本无关的功能不应因新变体被迫一起修改。
5. **选择复用形态与落点。** 同一机制的数值差异适合参数 / 预设；局部算法差异适合函数或策略；契约不相容或演进方向独立时保留独立实现。按下表决定交付形态，再沿现有资源与工作区规则确定实际位置。
6. **安排有区分力的验证。** 说明当前行为如何验收、已有行为如何保留，以及近期变化会用什么验证边界。验证只覆盖本次决定所需的风险；纸面走查、编译、运行与人工画质分别标明，不能把计划当成通过。

| 复用内容 | 交付形态与归属 |
|---|---|
| 开发方法、组织规范、标准代码骨架 | agent 的 knowledge / skill / template；按各库职责取用 |
| 程序实际共用、需要统一维护的计算或调度实现 | 项目或功能族共享库，按行为契约与实际消费者决定 |
| 独立变化的算法、设置、表现与适配 | 对应功能自身 |

模板更新不会自动升级既有产物。修改模板时检查受影响的已生成实现；修改共享实现时检查实际调用方。相似外形、相同代码行或“通用”名称都不足以单独决定归属。

## 开工说明示例

下面是资产生产工具的示例，按实际任务合并或省略无关项，不机械补满字段：

```text
参照基线：当前生产工具模板与一个实际消费者
稳定约定：Save=Load、保存保 GUID、自产与载入资产的所有权明确
近期变化：已有需求涉及 Texture3D；多输出是否需要仍未知
职责边界：生成服务 / 资产流程 / 设置与预览
暂定选择：当前只持有一个活动资产；多输出需求成立时重新评估
归属与复用：标准归 skill 模板，具体窗口归功能；算法另按契约判断
验证：载入不被预览替换；关窗只释放自产对象；三轴尺寸按真实资产取用
```

Research 把有关判断并入本轮假设；Production 并入修改计划；Experiment 在形成阶段 Plan 时标出待验证的假设。沿用各模式现有授权与验证流程。

## 演进与收尾

- 第一项功能建立当前必需的契约和清楚的局部边界。新真实变体出现后比较共性与差异，证据支持时再更新模板或提炼共享实现。
- 新功能反复要求修改无关实现、增加兼容分支或绕过公共流程时，重新检查职责边界；不要把所有差异都变成参数组合。
- 收尾将证实的共性与仍存的假设写回既有功能说明 / 模板 / 领域记忆，使下一项能找到当前合适的基线。保持正文唯一，历史 dated 记录不改写。

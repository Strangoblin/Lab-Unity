# 垃圾桶分流

> 垃圾桶是「还能还原的删除」，不是回收站之外的第二层缓存。留着不看的桶只占一个后果：
> 真需要 restore 的时候，你在一堆垃圾里找。

## 先看桶，不看文件

桶是一次 `delete` 调用的原子单位，`manifest.json` 记着当时的 `reason`、原路径、git 状态、
GUID 引用与 sha256。**整桶判断，不拆桶** —— 半个桶留在那里，manifest 就对不上了。

```bash
python3 .mcp/bin/cli.py trash          # 桶清单
python3 .agents/skills/structure-selfcheck/scripts/inventory.py   # 分类、年龄、体积
```

## 四类

| 类 | 判据 | 动作 |
|---|---|---|
| **生成物** | 顶层路径全部在 `tmp/**`、`tmp/*smoke`、隔离 fixture | 默认清空 |
| **退役子系统** | 顶层路径在 `.mcp/**`，且符号已不在活代码里 | 默认清空 |
| **业务资产** | 顶层路径在 `Assets/**` | **永不清空**，只有用户能定 |
| **其它 / 年轻桶** | 不匹配以上，或 < 7 天 | 默认保留，除非用户当场说清 |

分类是`inventory.py` 按路径前缀算的**起点**，不是结论。一个 `.mcp/` 桶里如果躺着一份还在被
引用的脚本，它就不是「退役子系统」—— 读 manifest 的 `reason` 和几个文件名再定。

## 复活四问

一个脚本要从垃圾桶回到 skill，四问全 yes：

1. **它是脚本吗** —— 不是数据、日志、截图、生成的报告
2. **会再出现吗** —— 解决的是仓库里反复出现的问题，不是一次性探针
3. **没有等价物吗** —— `.agents/skills/**/scripts/` 与 `.mcp/tests/` 里没有同样的能力
4. **还跑得起来吗** —— 剥掉被删对象的依赖、改完路径后，真跑一次通过

复活落点：`.agents/skills/<skill>/scripts/` + 该 skill 的 `scripts/README.md` 条目。
**跑不起来的就不是脚本，是资料** —— 不复活。

判据经常说「不」是正常的。一个什么都能捞回来的复活规则等于没有规则，只会把垃圾桶改名成
「第二技能库」。

## 清空留痕

`cli.py trash --empty <id>` 是整条自检流程里**唯一不可逆**的动作，和根 README 的红线
「trash 是唯一痕迹」直接冲突。处理方式是**先留痕，再清空**：

1. 往 `history.md` 追加一行：桶 id、时间、`reason` 原文、顶层路径、文件数、体积
2. 再 `trash --empty <id>`

`deletes.jsonl` 保留「谁在何时删了什么」，丢的只有内容。两者合起来仍然是完整审计链。

## 损坏的 manifest

盘点脚本会标 `[manifest 损坏]` —— 归档时已知有一例 `children` 被写成键名列表。
这种桶：

- **不要**因为脚本读不出子项就当它是空的
- 用 `cli.py restore <id>` 验证它还能恢复，能恢复就按类处理，不能恢复单独报给用户
- 损坏本身不构成清空理由（内容才是），但它是**先修 manifest 再清空**的理由

## 不要做的事

| 反例 | 为什么 |
|---|---|
| 「都在垃圾桶里了，一起清了吧」 | 业务资产桶混在其中。今天是删了又改的 shader，明天就是唯一副本 |
| 「这桶才 2 天，肯定还要用」 | 年龄不是内容。看 `reason`，别看时间戳 |
| 「先把桶清了，以后要再说」 | 清空之后再想要，就只剩 git —— 而未跟踪文件没有 git |
| 「manifest 说 sha256，不用看了」 | sha256 证明内容没变，不证明内容有用 |
